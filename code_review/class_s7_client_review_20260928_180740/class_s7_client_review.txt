2.1 8 线程 batchRead / batchWrite P50/P99

  你归档的 bench-results/latency_8thread_read.txt / _write.txt：

    read  threads=8 ops=8000 batch=16 calls=8000 wall_ms=3757.5 calls_s=2129.1
          latency_ms p50=0.321 p90=8.374 p99=61.537 p999=111.054 max=131.249 mean=3.610
    write threads=8 ops=8000 batch=16 calls=8000 wall_ms=3834.5 calls_s=2086.3
          latency_ms p50=0.331 p90=8.696 p99=62.060 p999=128.672 max=178.180 mean=3.734

  本会话用同一台机器的现有二进制复跑（同一命令）得到的是另一组数：

    read  threads=8 ops=8000 batch=16 calls=8000 wall_ms=1364.0 calls_s=5864.9
          latency_ms p50=0.099 p90=0.184 p99=31.621 p999=108.010 max=202.993 mean=1.196

  同一份代码、同一条命令，p50 差 3 倍、p90 差 45 倍。这不是“代码变了”，
  是单次采样的主机噪声。为把噪声变成结论，我做了线程扫描（每档 2 次）：

    threads  calls_s(约)   p50      p99       备注
    -------  -----------   ------   --------  --------------------------------
    1        7182 / 7207   0.077    0.19      单线程本底
    2        5933 / 5492   0.100    3.1~3.8   吞吐反而下降
    4        6258 / 6146   0.097    12.6~12.8 p99 随线程数线性抬头
    8        6173 / 5802   0.098    31.2~36.2 p99 ≈ 单线程的 160 倍

  结论（可写进简历/面试，但必须带条件）：
    · 吞吐不随线程数扩展，8 线程甚至低于单线程——因为业务调用在
      m_sdkMutex 与 open62541 内部 clientMutex 上双层串行（见第 3 节路径图 A）。
    · p99 随线程数单调上升，是排队（lock convoy），不是“偶发抖动”。
    · 单次 p99 不可复现。引用数字请用 `--repeats N` 的中位数。

2.2 断线恢复耗时分布

  归档 bench-results/recovery_distribution.txt：
    api_reconnect_ms      n=30 p50=149.3ms p90=157.3ms p99=247.5ms max=247.6ms mean=147.0ms
    restart_recovery_ms   n=20 p50=898.4ms p90=906.5ms p99=985.1ms max=1000.5ms mean=853.4ms

  本会话复跑（n 较小）：api p50=149.3 p99=194.0；restart p50=893.0 p99=901.3。
  两组一致，结论可信：
    · api_reconnect 的 ~149ms 主要是 disconnect() 的“轮询粒度”：
      每轮 callRunIterate(50ms) + sleep_for(50ms)，见 ua.cpp 的
      `callRunIterate` 与 `std::this_thread::sleep_for(std::chrono::milliseconds(50))`。
      它测的是封装层 API 往返，不是网络 RTT——面试时要主动说明。
    · restart_recovery ≈ 一个 watchdogIntervalMs（1000ms）+ connect，
      因为你把 watchdogIntervalMs 调到校验下限 1000ms。
    · 最坏多久转 GIVEN_UP 由 giveUpThresholdMs 决定（默认 60s）。

2.3 24h RSS 曲线：只有 4.6h，而且被污染

  bench-results/rss_curve.csv 用 scripts/check_rss.py 解析：
    rows=277 hours=4.60 first=7188KiB last=7212KiB delta=24KiB peak=7212KiB
    slope_h2=0.0KiB/h errors=0
  即：只跑了 4.6 小时（要求 24h），曲线确实是平的，errors=0。但——
  bench_rss 默认把 server 起在**同一个进程**里，而 residentKb() 读的是
  /proc/self/statm，于是这条“客户端 RSS 曲线”里含着 server 的内存。
  本会话改成独立进程后，同一台机器上客户端单独跑只有 5056KiB，
  比归档值低约 2.1MiB（条件不完全相同，但足以说明污染量级）。

  → 4.6h 的平线不能作为“客户端无泄漏”的证据；需要 24h + 独立 server 重跑。

3. 以官方源码为准的 SDK 运行事实与路径图
================================================================================
（行号均来自本机 v1.4.14 源码。）

[A] 客户端没有自己的线程，必须周期调用 UA_Client_run_iterate
    include/open62541/client.h:46-50 原文：
      "**However**: At this time, the client does not yet contain its own thread
       or event-driven main-loop, meaning that the client will not perform any
       actions automatically in the background. ... The user will have to
       periodically call `UA_Client_run_iterate` to ensure that asynchronous
       events are handled, including keeping a secure connection established."
    对应封装：Impl::runWatchdog() → callRunIterate()（ua.cpp）。

[B] UA_Client_run_iterate 在 event loop 期间**释放** SDK 自己的 clientMutex
    src/client/ua_client.c:1043-1058 原文：
      UA_Client_run_iterate(UA_Client *client, UA_UInt32 timeout) {
          lockClient(client);
          UA_StatusCode rv = __UA_Client_startup(client);
          unlockClient(client);
          ...
          /* All timers and network events are triggered in the EventLoop. Release the
           * client lock before. The callbacks from the EventLoop take the lock
           * again. */
          UA_EventLoop *el = client->config.eventLoop;
          rv = el->run(el, timeout);      // ← 最多阻塞 timeout 毫秒，此时 clientMutex 已释放
          ...
      }
    这是本轮延迟分析的关键：那 50ms 的阻塞**只被封装层的 m_sdkMutex 持有**，
    不是被 SDK 持有。也就是说，是封装自己把业务线程挡在门外。

[C] 同步服务调用全程持有 SDK clientMutex
    src/client/ua_client.c:668-673 原文：
      __UA_Client_Service(UA_Client *client, const void *request, ...) {
          lockClient(client);
          __Client_Service(client, request, requestType, response, responseType);
          unlockClient(client);
      }
    UA_Client_Service_read/write 都走这里。所以 8 线程业务调用在 SDK 层
    本来就会串行；封装层的 m_sdkMutex 是在此之上再加一层。

[D] isFullyConnected 看 noSession，而不是 noReconnect/noNewSession
    src/client/ua_client_connect.c:121-129 原文：
      isFullyConnected(UA_Client *client) {
          if(client->sessionState != UA_SESSIONSTATE_ACTIVATED && !client->config.noSession)
              return false;
          if(client->channel.state != UA_SECURECHANNELSTATE_OPEN)
              return false;
          ...
    结论：封装固定 noReconnect/noNewSession=true，但同步服务调用前的补连仍会走
    connectSync。

[E] noReconnect / noNewSession 的真实语义
    client.h:112-116 原文：
      "noReconnect; /* Don't reconnect SecureChannel when the connection
                     * is lost without explicitly closing. */"
      "noNewSession; /* Don't automatically create a new Session when
                      * the intial one is lost. Instead abort the
                      * connection when the Session is lost. */"
    → noReconnect 不阻止同步服务调用前的 connectSync；noNewSession 才会在
      会话丢失时主动断开通道。

3.1 路径图 A：延迟尾巴的根因（业务调用 vs 看门狗 runIterate 争 m_sdkMutex）
--------------------------------------------------------------------------------

    业务线程 batchRead                         看门狗线程 runWatchdog()
    ------------------                         -----------------------
    lock(m_sdkMutex)  ──┐                       callRunIterate()
                        │ 竞争                  └─ lock(m_sdkMutex)  ← 先到者持有
    __UA_Client_Service │                          UA_Client_run_iterate(c, 50)
      lockClient()      │                            lockClient(); __UA_Client_startup(); unlockClient();
      ... 阻塞 ...      │                            el->run(el, 50)   ← 最多 50ms（SDK 锁已释放）
      unlockClient()    │                          unlock(m_sdkMutex)
    unlock(m_sdkMutex) ─┘
                                                   等 100ms
                                                   ... 循环 ...

    · 看门狗每轮先 sleep_for(100ms)，再 callRunIterate(50ms)。在 chain
      空闲时，那 50ms 是实打实的阻塞；业务线程想进 service 就得排队。
    · 线程扫描的数据与之吻合：p99 随并发线程数单调上升。
    · 修复方向（本轮未强改，属判断题）：给 callRunIterate 加 timeout 形参，
      看门狗路径传 0（非阻塞 iterate + 100ms 轮询），connect/disconnect
      的轮询路径保留 50ms。这样既不丢事件，又消掉 50ms 的锁持有。
      这是“面试会被问、且你有数据支撑”的取舍点。

--------------------------------------------------------------------------------
3.2 路径图 B：bench 自带 server 忙等一个核
--------------------------------------------------------------------------------

    bench_common.h::Server::startServing()
      thread_ = std::thread([this] {
        while (running_) UA_Server_run_iterate(server_, false);   // ← waitInternal=false
      });

    src/server/ua_server.c:808-820 原文：
      UA_Server_run_iterate(UA_Server *server, UA_Boolean waitInternal) {
          UA_EventLoop *el = server->config.eventLoop;
          if(!el) return 0;
          UA_UInt32 timeout = (waitInternal) ? UA_MAXTIMEOUT : 0;   // ← false → 0
          el->run(el, timeout);                                     // ← 立即返回
          ...
      }
    → false 时 el->run(…,0) 立即返回，while 变成纯忙等，占满一个 CPU 核。
      在一台 4 核 8 线程的机器上，它同时和 8 个业务线程 + 1 个看门狗抢 CPU，
      会把 p99 推高。这就是为什么同一个 benchmark 在不同机器/不同负载下
      能差 45 倍。本轮改为 waitInternal=true（事件驱动阻塞，由 1s 的
      housekeeping 回调兜底唤醒），见补丁。

3.3 路径图 C：同一 UA_Server* 可以 stop/start（证明 restart benchmark 合法）
--------------------------------------------------------------------------------

    bench_recovery 用 server->stopServing()/startServing() 模拟服务端宕机。
    官方源码证明这是受支持的：
      ua_server.c:677  UA_Server_run_startup 开头：
        if(server->state != UA_LIFECYCLESTATE_STOPPED) {

8.2 会被追问（先想好答案）
  · “为什么 8 线程吞吐还不如单线程？”
    → 引路径图 A：m_sdkMutex 覆盖整次 service；open62541 自身 clientMutex
      也串行；SDK 无后台线程，事件循环单线程。多线程在这里是并发安全，
      不是并行吞吐。承认边界，给出“多连接/连接池”的演进方向。
  · “p99 60ms 怎么回事？”
    → 先说单次不可复现（p90 8.4ms vs 0.18ms），再说已用线程扫描把
      “随线程数上升”钉死，根因是排队；并指出不可以在简历里只写一个
      max=178ms 的恐怖数字。
  · “noReconnect=true 还能恢复吗？”→ 能，引 [D]：isFullyConnected 看 noSession。
  · “noNewSession=true 会怎样？”→ 会话失效即主动断开（引 [E]）。
  · “MockSdk 与真实 SDK 差异？”→ 见 limitations 第 3 节，主动承认哪些结论
    必须由真实 server 用例（T110/T116/T117）与 netem 保证。
  · “include/PLC/* 为什么在公开 include 树？”→ 本轮已删除三份重复；
    剩余 include/PLC 属内部转换层，公共入口只有 OPCUAPacking/ua.h。
