2.1 官方事实清单（v1.4.14）
--------------------------------------------------------------------------------
[A] 客户端没有自己的线程/事件循环，必须周期调用 UA_Client_run_iterate
    出处：include/open62541/client.h 顶部 Client 章节原文
      "the client does not yet contain its own thread or event-driven main-loop ...
       The user will have to periodically call UA_Client_run_iterate to ensure that
       asynchronous events are handled, including keeping a secure connection
       established."
    对应你的实现：Impl::runWatchdog() + callRunIterate()。方向正确。

[B] 同步服务调用会自动补连（与 noReconnect 无关）
    出处：src/client/ua_client.c  __Client_Service()
      if(!isFullyConnected(client)) {
          UA_LOG_INFO(..., "Re-establish the connction for the synchronous service call");
          connectSync(client);
          if(client->connectStatus != UA_STATUSCODE_GOOD) {
              respHeader->serviceResult = client->connectStatus;
              return;
          }
      }
    其中 isFullyConnected() 在 src/client/ua_client_connect.c:122：
      sessionState==ACTIVATED(除非 noSession) && channel.state==OPEN &&
      endpoint 已配置 && discoveryUrl 非空 && 无未完成握手
    connectSync() 在 ua_client_connect.c:1789：initConnect() → TCP/HEL/ACK/OPN。
    结论：你在 Impl 头注释里写的
      "noReconnect 仅禁止通道被动关闭后的后台自动重连，不禁止服务调用前的补连"
    完全正确。noReconnect 的唯一影响在 ua_client_connect.c:1398 的被动状态机：
      case UA_SECURECHANNELSTATE_CLOSED:
          if(client->config.noReconnect)
              client->connectStatus = UA_STATUSCODE_BADNOTCONNECTED;
          else
              initConnect(client);
          return;
    noNewSession 才是"会话丢失即断开"：ua_client.c:472 在收到
      BADSESSIONIDINVALID / BADSESSIONCLOSED 时 cleanupSession + closeSecureChannel。

[C] 哪些函数是线程安全的
    官方 doc/building.rst UA_MULTITHREADING：
      "0-99: Multithreading support disabled.
       >=100: API functions marked with the UA_THREADSAFE-macro are protected
       internally with mutexes. Multiple threads are allowed to call these functions
       of the SDK at the same time without causing race conditions."
    本构建 build/src_generated/open62541/config.h: UA_MULTITHREADING 100。
    你实际用到的 UA_Client_run_iterate / UA_Client_getState / __UA_Client_Service /
    UA_Client_Service_read/write / UA_Client_connect*/disconnect* 全部带 UA_THREADSAFE。
    因此：SDK 已经在内部用 client->clientMutex 串行化，你的 m_sdkMutex 是"第二把锁"。

[D] 配置是浅拷贝、插件所有权随之转移（这决定了 RealSdk 的日志写法是否安全）
    出处：client.h
      UA_Client_newWithConfig():
        "Creates a new client. Moves the config into the client with a shallow copy.
         The config content is cleared together with the client."
      UA_ClientConfig_copy() 注释:
        "It makes a shallow copy of all the plugins from source to destination.
         Therefore calling _clear on the dst object will also delete the plugins in
         src object."
    实现：ua_client.c:107 UA_Client_newWithConfig() 直接 client->config = *config;
    释放：ua_client.c:202 UA_Client_delete() → UA_ClientConfig_clear() →
          if(config->logging != NULL && config->logging->clear != NULL)
              config->logging->clear(config->logging);
    默认 logger 是堆分配：plugins/ua_config_default.c:1120
          if(config->logging == NULL)
              config->logging = UA_Log_Stdout_new(UA_LOGLEVEL_INFO);
          （plugins/ua_log_stdout.c: UA_Log_Stdout_new 里 UA_malloc + clear=UA_Log_Stdout_clear）
    结论：RealSdk::clientNew() 里"就地复用默认 logger、保留 clear"是安全的，
          本地 cfg_ 之后不能再 clear（否则二次释放）。你的注释是对的。

2.5 路径图 D：两把锁
--------------------------------------------------------------------------------
  你的封装层:  std::recursive_mutex m_sdkMutex        [ua.cpp]
       └─ open62541 内部: client->clientMutex          [UA_MULTITHREADING>=100]
             └─ EventLoop elMutex / 日志 logSpinLock
  锁序恒定（先 m_sdkMutex 再 clientMutex），不会 ABBA 死锁。
  但语义重叠：SDK 已经保证 UA_THREADSAFE；m_sdkMutex 的价值只剩"把多个 SDK 调用

  这一点在面试里是很好的讨论题，但要在文档里说清楚，否则会被认为"重复造锁"。

3.1 资源泄漏（特别是 UA_ReadResponse 出口路径）          结论：正确，A-
--------------------------------------------------------------------------------
好消息（这部分你做得很扎实，面试可以主动讲）：
  - ReadResponseGuard / WriteResponseGuard / ReadRequestGuard / WriteRequestGuard
    四个 RAII 覆盖了 batchRead/batchWrite 的
    "正常返回 / 重试 / 预算超限 / 逐项错误 / 提前参数校验失败 / 服务层错误 / 畸形响应"
    全部出口。批读里的 response 声明在 for 循环体内，Guard 随之每轮构造/析构，
    重试路径不会累积。
  - Guard 的"畸形响应"防御是必要的：UA_Array_delete(p, size, type) 在
    size>0 && p==nullptr 时会先对 p 做指针步进/成员清理（对非 pointerFree 类型
    会解引用），把 resultsSize 先归零是有效的兜底，不是多余的。

需要修的（真实缺陷，已在补丁中修复）：
  (R1) RealSdk::clientNew 的 OOM 泄漏。原文：
        UA_StatusCode rc = UA_ClientConfig_setDefault(&cfg_);
        if (rc != UA_STATUSCODE_GOOD) {
          return nullptr; // 让 create()/createWithSdk() 走失败分支
        }
        ...
        client = UA_Client_newWithConfig(&cfg_);
      问题：setDefault 在返回 BADOUTOFMEMORY 之前可能已经分配了
      logger / eventLoop / securityPolicies；UA_Client_newWithConfig 失败时
      所有权也仍在 cfg_。两种失败都会把这些插件泄漏掉。
      补丁：两处失败分支补 UA_ClientConfig_clear(&cfg_)。

  (R2) 例外安全缺口（建议，未打补丁）：batchRead 在拿到 response 后进入
      std::vector::reserve/push_back 与 std::string 构造，可能抛 std::bad_alloc；
      Guard 会正确清理，但异常会穿透 Result 契约。建议在公共入口 try/catch
      转成 RichError::INTERNAL_ERROR。

3.2 配置快照与悬垂指针                                  结论：快照安全；析构有 UB
--------------------------------------------------------------------------------
好消息：
  - ClientConfig 是纯值类型（int/uint32_t/int64_t/enum），create 入参按值拷贝、
    Impl::m_config 再拷贝一份，调用方事后修改自己的 cfg 不影响实例。
  - endpointUrl 在 Impl 与 RecreateSync 各存 std::string 拷贝；
    connect() 里 endpointUrl.c_str() 指向成员，生命周期覆盖整个调用。
  - 回调上下文所有权链是正确的：
      Impl::m_callbackContext (shared_ptr)
      UA_ClientDeleter::ctx     (shared_ptr)   ← 随 shared_ptr<UA_Client> 快照复制
      config->clientContext     (raw ptr)
    即使 Impl 先析构，Deleter 仍持有 ctx，直到最后一个 UA_Client 引用释放，
    因此 stateCallback/inactivityCallback 里的 UA_Client_getContext 不会悬垂。
    这是全项目里最漂亮的一处设计之一。

必须修的（真实 UB，已在补丁中修复）：
  (D1) 析构与 recreateGiveUpClient() 竞争。原文：
        if (!m_recreateSync->m_recreateCv.wait_for(
                lock, std::chrono::seconds(10),
                [&] { return !m_recreateSync->m_recreating; })) {
          // 记录 fatal 日志, 走强制清理路径
          // (不抛异常, 不 terminate)
        }
      问题：recreateGiveUpClient() 在交换 pImpl 前后仍会解引用 this->pImpl /
      this->m_recreateSync。10s 超时后析构继续执行，本对象被销毁，而 recreate
      线程可能仍在访问已释放对象 → use-after-free（可能表现为偶发崩溃或
      LSan 报"still reachable"，也可能悄悄把新 Impl 装回已析构对象造成泄漏）。
      修复：改为无超时等待，直到 RecreateGuard 置 m_recreating=false。
      由于 ApiLease 已把普通 API 在 m_terminated 后挡在门外，recreate 是唯一
      还会访问 this 的路径，而且它有界（drain 2s + connect 超时），不会挂死。

  (D2) ThreadGuard 自 join（潜在 terminate）。原文：
        ~ThreadGuard() {
          if (m_watchdogThread && m_watchdogThread->joinable()) {
            m_watchdogCv.notify_all();
            m_watchdogThread->join();
          }
        }
      问题：joinWatchdog() 已经防了"当前线程就是 watchdog 就不 join"，
      但 ThreadGuard 没防。一旦 ~Impl 在 watchdog 线程上执行（未来重构、
      或最后一个 shared_ptr 在 runWatchdog 里释放），join 自己会抛
      std::system_error，析构函数内抛出即 std::terminate。
      修复：与 joinWatchdog() 同样的 get_id() 判断。

3.3 线程安全（基于 v1.4.14 实际行为）                    结论：B
--------------------------------------------------------------------------------
事实基础见 2.1[C]。总体评价：
  - m_connState 用 CAS 做 connect/disconnect 单飞；m_lifeState 用 CAS 做
    RUNNING/RECOVERING/GIVEN_UP 迁移，且 TurnToRunning()/setGiveUpSignal()
    都刻意用 CAS 防"丢失更新"。这比大多数作品的"一把大锁"更细，值得讲。
  - InFlightGuard(m_taskCounter) 与 ApiLease(m_inFlight) 是两套计数器，
    分别服务 shutdown() 与 recreateGiveUpClient()，边界清晰。
  - watchdog 只读原子/加锁取 shared_ptr 快照，回调只碰原子，规矩执行的很好。

扣分项：
  (C1) m_sdkMutex 与 SDK 内部 clientMutex 语义重叠（见 2.5）。功能上安全，
       但会放大阻塞；且它让"重连权威在看门狗"的直觉失效（见 2.1[B]，业务
       线程自己也会触发 connectSync）。建议：要么删掉 m_sdkMutex、依赖 SDK
       的 UA_THREADSAFE；要么保留但在公共头明确"任何一次 batchRead 都可能
       同步补连并阻塞最长 timeout"。
  (C2) m_connState 同时表示 connect 与 disconnect 的进行态（都写 CONNECTING），
       语义被合并。make 到 THREADBUSY 时无法区分"正在连"还是"正在断"。
       建议拆成 CONNECTING/DISCONNECTING 两个状态，或至少把返回值区分开。
  (C3) shouldTriggerGiveUp() 读 m_lastBadStatusMs 没持 m_BadStatusMsMx。
       因为它是 atomic，不是数据竞争，只是 check-then-act 非原子，属于良性；
       但与 updateBadStatusTime()/resetGiveUpTimer() 的加锁风格不一致，
       顺手统一即可。
  (C4) 现有 TSan 用例很强（T25/T40/T41/T42/T91/T108...），但除 T5/T99 外
       多数是 Mock 上的并发。真实 SDK 的并发路径建议再加一条真实服务器版本。

3.4 Rule of Five 与移动语义                             结论：A-
--------------------------------------------------------------------------------
  - OPC_UA_Client 拷贝/移动全删、析构非平凡、final，编译期断言钉死
    （tests/compile/RuleOfFiveAsserts.cpp），这正是"不可移动/不可拷贝"的正确理由：
    它持有 shared_ptr<Impl>、watchdog 线程、以及被 SDK 回调以 raw ptr 引用的
    CallbackContext，按值搬走会让"线程内 this"和回调上下文地址失效。
  - 领域值类型 noexcept 移动断言齐全，保证 vector 扩容走移动而不是深拷贝。

  唯一建议：NodeId 目前是聚合体，`ns` 无范围校验、`dataType` 与
  batchWrite 的 ValueType 是两处独立输入，靠运行期 get_if 校验。
  可考虑一个 `makeNodeId` 工厂或构造期校验，把非法组合挡在编译/入口处。

--------------------------------------------------------------------------------
  - ua.h 不包含任何 open62541 头，只前向声明 ISdk，ReadResult/WriteResult 用

    这是把"封装完整"变成可证伪构建产物的好做法，比写一堆注释强。
  - 需要修的（建议）：
    (E1) 后门可被冒用。原文：
           friend struct ClientTestHooks; // ← 只给钩子开一扇门
         友元是授予"全局命名空间里叫 ClientTestHooks 的类型"。任何 TU 只要

4.1 现有资产盘点（这是你最强的地方，务必在简历/面试里讲）
--------------------------------------------------------------------------------
  - 31 个 test 文件、100+ 用例，编号 T1~T109 + TC/TA/T8B/T8C + B1~B3；
  - tests/include/MockSdk.h 是一个 882 行的可编程 fake SDK：
    mode / 虚拟时钟 / state 队列 / read&write 脚本 / 响应形状 / 逐项状态 /
    标量&数组&字符串播种 / 阻塞钩子 / 在途计数 / clientNew&Delete 计数；
  - tests/util/ClientTestFixture.cpp 起真实 open62541 server（每用例独立端口）；
  - .github/workflows/sanitizers.yml 四 job：ASan+UBSan / LSan / TSan / flaky
    （--gtest_repeat=50 --gtest_shuffle）；
  - scripts/run_tsan.sh 还会做"并发用例过滤器覆盖审计"，漏测就 exit 1；
  - 编译期探针：only_ua_h（封装）、RuleOfFiveAsserts（五法）。
  这套测试框架的成熟度，比很多有 3 年经验的候选人都高。

4.2 仍然存在的缺口（按价值排序）
--------------------------------------------------------------------------------
  (G1) 真实 socket 的"断开-恢复"从未被测试。
       fixture 里 stopServer()/restartServer()/serverIsAccepting() 三个函数
       定义了但全项目零调用；而这条路恰好是 2.1[B] 里 connectSync 自动补连 +
       watchdog 自愈的核心场景。Mock 无法替代：它测不到 TCP 断开、
       stateCallback 被动置 BADNOTCONNECTED、以及 reconnect 的所有权时序。
       → 新增 T110。

  (G2) 单进程多实例隔离从未被测试。所有用例都是"一个 server + 一个 client"。
       现实中一个采集进程会同时持多个 PLC 连接；一个实例 shutdown 不能影响
       另一个，且共享的日志/全局状态不能串。
       → 新增 T112。

  (G3) "规模"维度缺失。没有大 batch 用例，UA_Array_new /
       UA_ReadRequest_clear / UA_ReadResponse_clear / 结果 vector 只在
       N=1~3 上验证过。
       → 新增 T111（1024 项）。

  (G4) 空/缺失 STRING 变体的错误码不确定。readTraits 对 data==nullptr 走
       RichError(string) → UNKNOWN 兜底，而同类标量路径返回 TYPE_MISMATCH，
       同一个"值不合法"在两个分支给出不同错误码。
       → 新增 T113（修复前必失败，是红→绿回归）。

  (G5) 析构 vs recreate 没有廉价回归（D1 的行为差异在 10s 处才显现，写进
       CI 会让单条用例 >10s）。本次只给修复 + 代码走查论证，不强行加慢用例。

  (G6) run_asan.sh / run_lsan.sh 目前把全部 Client* 用例塞进一个进程跑。
       一条用例泄漏会污染整批日志、难以归因。建议按 Suite 分片，和 run_tsan.sh
       一样分组执行并在脚本里打印每组匹配数。

  (G7) T5 用 8 线程 ×50 次、断言 ≥99% 成功，成功率受调度影响；建议在真实
       SDK 上补一条"读到的值必须 ∈ 写入集合"的 TSan 版本（T99 已有 Mock 版）。

4.3 对"测试结果是否足够"的直接回答
--------------------------------------------------------------------------------
  足够的部分：CRUD、逐项错误映射、类型矩阵（12 个 S7 类型）、畸形响应、
             预算/重试边界、Config 校验矩阵、生命周期幂等、Rule of Five、
             封装完整性——这些已经覆盖得比绝大多数作品细。
  不足的部分：真实网络时序、多实例、规模、确定错误码。
  换句话说：你的测试证明的是"控制流正确"，还不能证明"真实工业现场的所有权与
  时序正确"。T110~T113 就是把后者补上。

+void ClientTest::stopServerAndJoin() {
+    if (!server_ || !serverStarted_)
+        return;
+    // 先让迭代线程准备退出，再停事件循环把它从 run_iterate(wait=true) 唤醒，
+    // 最后 join，确保之后 run_startup 不会与旧迭代线程并发访问 server_。
+    running_.store(false, std::memory_order_release);
+    UA_Server_run_shutdown(server_);
+    serverStarted_ = false;
+    if (serverThread_.joinable()) {
+        serverThread_.join();
+    }
+}

+void ClientTest::startServerThread() {
+    if (!server_ || serverStarted_)
+        return;
+    UA_StatusCode rc = UA_Server_run_startup(server_);
+    if (rc != UA_STATUSCODE_GOOD) {
+        throw std::runtime_error("UA_Server_run_startup (restart) failed");
+    }
+    serverStarted_ = true;
+    running_.store(true, std::memory_order_release);
+    serverThread_ = std::thread([this] {
+        while (running_.load(std::memory_order_acquire)) {
+            UA_Server_run_iterate(server_, true);
+        }
+    });
