2. 以官方代码/文档为准的 SDK 运行事实
================================================================================
（以下引用全部来自本机 v1.4.14 源码，行号为该文件真实行号。）

[A] 客户端没有自己的线程，必须周期调用 UA_Client_run_iterate
    include/open62541/client.h:46-50 原文：
      "**However**: At this time, the client does not yet contain its own thread
       or event-driven main-loop, meaning that the client will not perform any
       actions automatically in the background. ... The user will have to
       periodically call `UA_Client_run_iterate` to ensure that asynchronous
       events are handled, including keeping a secure connection established."
    对应封装：Impl::runWatchdog() → callRunIterate()（ua.cpp 内）。

[B] isFullyConnected 看 noSession，而不是 noReconnect/noNewSession
    src/client/ua_client_connect.c:121-129 原文：
      UA_Boolean
      isFullyConnected(UA_Client *client) {
          /* No Session, but require one */
          if(client->sessionState != UA_SESSIONSTATE_ACTIVATED && !client->config.noSession)
              return false;
          /* No SecureChannel */
          if(client->channel.state != UA_SECURECHANNELSTATE_OPEN)
              return false;
          ...
    结论：封装把 noReconnect / noNewSession 固定为 true，但 isFullyConnected
    只受 noSession 影响 → 同步服务调用仍会走 connectSync。

[C] noReconnect 的真实语义：只禁止“被动失联后的后台重连”
    client.h:112-113 原文：
      "noReconnect; /* Don't reconnect SecureChannel when the connection
                     * is lost without explicitly closing. */"
    → 不阻止同步服务调用前的 connectSync 补连。

[D] noNewSession 的真实语义：会话失效即主动断开通道
    client.h:114-116 原文：
      "noNewSession; /* Don't automatically create a new Session when
                      * the intial one is lost. Instead abort the
                      * connection when the Session is lost. */"
    src/client/ua_client.c:465-487 原文：
      if(responseType != &UA_TYPES[UA_TYPES_ACTIVATESESSIONRESPONSE] &&
         (response->responseHeader.serviceResult == UA_STATUSCODE_BADSESSIONIDINVALID ||
          response->responseHeader.serviceResult == UA_STATUSCODE_BADSESSIONCLOSED)) {
          cleanupSession(client);
          if(client->config.noNewSession) {
              client->connectStatus = response->responseHeader.serviceResult;
              ...
              closeSecureChannel(client);
          } else { ... }
      }
    结论：noNewSession=true 时 SDK 不会在服务调用里自动重建会话，而是关通道、
    把 connectStatus 置成具体 Bad 码。恢复会话的责任落回封装层。

[E] 同步服务调用会自动补连
    src/client/ua_client.c:570-578 原文：
      if(!isFullyConnected(client)) {
          UA_LOG_INFO(..., "Re-establish the connction for the synchronous service call");
          connectSync(client);
          if(client->connectStatus != UA_STATUSCODE_GOOD) {
              respHeader->serviceResult = client->connectStatus;
              return;
          }
      }

[F] initConnect 在通道未 CLOSED 时直接返回
    src/client/ua_client_connect.c:1698-1701 原文：
      UA_LOG_WARNING(client->config.logging, UA_LOGCATEGORY_CLIENT,
                     "Client connection already initiated");
      return;
    → 通道还 OPEN/CONNECTING 时，connect()/connectSync() 都无法真正重建会话。

[G] StatusCode 的“坏”必须按 severity 位判断，不能与泛型码等号比较
    include/open62541/types.h:161-166 原文：
      /* Extracts the severity from a StatusCode. See Part 4, Section 7.34 */
      UA_INLINABLE(UA_Boolean
                   UA_StatusCode_isBad(UA_StatusCode code), {
          return ((code >> 30) >= 0x02);
      })
    → UA_STATUSCODE_BADSESSIONIDINVALID=0x80250000 与 UA_STATUSCODE_BAD=0x80000000
      永不相等；isConnectBad() 已改用 UA_StatusCode_isBad()（正确）。

[H] disconnectAsync 必须被 run_iterate 驱动到 CLOSED
    client.h:468-469 原文：
      "/* Disconnect async. Run UA_Client_run_iterate until the callback
       * notifies that all connections are closed. */"
    → 封装用 getState 轮询 CLOSED 是正确方向；但“有界性”必须由封装自己保证。

[I] UA_Array_new 零初始化，因此“半成品请求被 clear”不会踩脏内存
    src/ua_types.c:1937 起原文：
      UA_Array_new(size_t size, const UA_DataType *type) {
          if(size > UA_INT32_MAX) return NULL;
          if(size == 0) return UA_EMPTY_ARRAY_SENTINEL;
          return UA_calloc(size, type->memSize);
      }
    → batchRead/batchWrite 先设 *_Size 再逐项 init，中途失败时后续槽位是
      calloc 的 0，ReadRequestGuard/WriteRequestGuard 的 clear 是安全的。
      （这是本轮核对后“确认不是缺陷”的一条，面试时可以主动讲。）

2.2 路径图 B：看门狗裁决树
--------------------------------------------------------------------------------
  runWatchdog()
   └─ 每 watchdogIntervalMs → doWatchdogDecision()
        ├─ isConnected()（run_iterate + getState）→ 刷新三元组
        ├─ healthy? → TurnToRunning(); return
        └─ !healthy:
             ├─ connectionLost || session != ACTIVATED
             │     → updateBadStatusTime; shouldTriggerGiveUp? → TurnToGiveup
             │     → disconnect() → connect()
             ├─ !isChannelClosed()（通道 OPEN）
             │     → updateBadStatusTime; shouldTriggerGiveUp? → TurnToGiveup
             │     → callRunIterate; 仍非 CLOSED → TurnToRecovring; 否则 connect()
             ├─ isConnectBad() || !isHealthyCached()
             │     → updateBadStatusTime; shouldTriggerGiveUp? → TurnToGiveup
             │     → disconnect() → connect()
             └─ else → TurnToRunning()   （只有 isHealthyCached() 为真才可达）

--------------------------------------------------------------------------------
2.3 路径图 C：connect()/disconnect() 的失败出口（本轮 2 个缺陷所在）
--------------------------------------------------------------------------------
  Impl::connect()
   ├─ CAS IDLE→CONNECTING；connectAsync()
   │    └─ 非 GOOD → return CONNECT_FAILED      ★ 缺陷 1a：不迁移 LifeState
   └─ while(true):
        isConnected()（run_iterate + getState）
        ├─ 三元组健康 → TurnToRunning(); success
        └─ elapsed > timeoutMs || wallDeadline:
             isConnected() 复核
             disconnectAsync()
             return TIMEOUT_NOTCONNECT            ★ 缺陷 1b：不迁移 LifeState

  Impl::disconnect()
   ├─ CAS IDLE→CONNECTING；disconnectAsync()
   │    └─ 非 GOOD → return DISCONNECT_FAIL     ★ 缺陷 2a：不迁移 LifeState
   └─ while(true):
        isConnected()；channel==CLOSED → TurnToRecovring(); success
        └─ elapsed > timeoutMs || wallDeadline:
             getState()；cs==CLOSED → TurnToRecovring(); success
             否则 disconnectAsync(); return TIMEOUT_NOTDISCONNECT
                                                 ★ 缺陷 2b：不迁移 LifeState

  两条路径的共同点：成功出口已经会离开 RUNNING，失败出口不会。于是当失败发生
  时缓存三元组已经处于“不健康”形态（如 channel CLOSED / CONNECTING），就出现
  RUNNING 与 isHealthy()==false 并存。

4.1 【已修，红→绿】connect() 失败出口不迁移 LifeState
--------------------------------------------------------------------------------
问题原文（src/OPCUAPacking/ua.cpp，Impl::connect()，修复前）：
    UA_StatusCode retval =
        m_sdk->connectAsync(client.get(), endpointUrl.c_str()); // ★
    if (retval != UA_STATUSCODE_GOOD) {
      return Result<Unit, ConnectErrorState>::error(
          ConnectErrorState::CONNECT_FAILED);
    }
    ...
      {
        std::lock_guard<std::recursive_mutex> lock(m_sdkMutex);
        m_sdk->disconnectAsync(client.get()); // ★
      }
      return Result<Unit, ConnectErrorState>::error(
          ConnectErrorState::TIMEOUT_NOTCONNECT);

对照文档契约（include/OPCUAPacking/Types.h，原文）：
      /// 三元组全部就绪：
      ///   sdkConnectStatus == GOOD
      ///   sdkChannelState  == OPEN
      ///   sdkSessionState  == ACTIVATED
      /// 由 TurnToRunning() 置位（看门狗判定健康时）。
      RUNNING,

后果：当公开 connect() 在“缓存三元组已经不健康”时失败（例如链路静默失效，
  getState 报 (GOOD, CLOSED, CLOSED)），两个失败出口直接 return，lifeState 停在
  RUNNING；同一时刻 isHealthy() 必然失败。于是 checkLifeState()==RUNNING 与
  isHealthy()==false 同时成立，RUNNING 的充要条件被破坏。
为什么现有测试看不见：T58 只断言 CONNECT_FAILED→SERVICE_FAILED 与 CAS 复位；
  T74 只断言超时后调用了一次 disconnectAsync；T120 从 create() 进入、失败后对象
  直接销毁，都不读 checkLifeState()。

7. Benchmark / 耐久：具体指令（直接回答报告第 7 节第 8 项）

7.0 一次性构建

  cd /root/Cross_platform_file_transfer_tool-main/Cross_platform_file_transfer_tool-main
  export OPEN62541_ROOT=/root/open62541-v1.4.14-noSanitizer

  # 方式 A：一键（自动 configure + build + 跑三项）
  ./scripts/run_bench.sh

  # 方式 B：手动
  cmake -B build-bench -DCMAKE_BUILD_TYPE=RelWithDebInfo \
        -DCMAKE_C_COMPILER=clang-17 -DCMAKE_CXX_COMPILER=clang++-17 \
        -DCMAKE_TOOLCHAIN_FILE=conan_debug_build/conan_toolchain.cmake \
        -DOPEN62541_ROOT="$OPEN62541_ROOT"
  cmake --build build-bench --target bench_latency bench_recovery bench_rss -j
  # 产物：build-bench/bench-build/bench_{latency,recovery,rss}

  说明：bench 默认自己起一个 in-process open62541 server（127.0.0.1），
  所以每条命令都能单机复现；也可用 --endpoint 指向真实设备。

7.1 8 线程 batchRead P50/P99

  # 读，batch=16
  ./build-bench/bench-build/bench_latency --threads 8 --ops 8000 --batch 16 \
    | tee bench-results/latency_8thread_read.txt

  # 写
  ./build-bench/bench-build/bench_latency --threads 8 --ops 8000 --batch 16 --write \
    | tee bench-results/latency_8thread_write.txt

  # 批量大小敏感性（面试常问“batch 多大合适”）
  for b in 1 16 128; do
    ./build-bench/bench-build/bench_latency --threads 8 --ops 4000 --batch "$b"
  done | tee bench-results/latency_batch_sweep.txt

  输出示例（格式固定，便于贴进报告）：
    mode=read threads=8 ops=8000 batch=16 calls=8000 wall_ms=... calls_s=... items_s=... errors=0
    latency_ms p50=... p90=... p99=... p999=... max=... mean=...
  解读：errors 必须为 0；p99/p50 比值反映排队（m_sdkMutex 串行化）程度；
  batch 增大时 calls_s 下降、items_s 上升，用于选型。

7.2 断线恢复耗时分布

  ./build-bench/bench-build/bench_recovery --api-cycles 30 --restart-cycles 20 \
    | tee bench-results/recovery_distribution.txt

  输出示例：
    api_reconnect_ms   n=30 p50=...ms p90=...ms p99=...ms max=...ms mean=...ms
    restart_recovery_ms n=20 p50=...ms p90=...ms p99=...ms max=...ms mean=...ms
  解读：
    api_reconnect_ms    = 显式 disconnect()+connect() 的往返，反映 API 路径开销；
    restart_recovery_ms = 服务端宕机 → 看门狗发现 → 服务端恢复 → isHealthy()
                          再次成功。它天然受 watchdogIntervalMs（校验下限 1000ms）
                          支配，p99 约等于一个 watchdog 周期 + connect 时间。
  面试表述：不要只说“能自愈”，要给出“检测 + 重建”两段耗时及其受配置支配的
  关系，并说明 giveUpThresholdMs 决定最坏多久转 GIVEN_UP。

7.3 24h RSS 曲线

  # 先跑 36s 冒烟，确认 CSV 正常
  ./build-bench/bench-build/bench_rss --hours 0.01 --interval 5 --hz 20

  # 正式 24h（建议 nohup；机器不要休眠）
  nohup ./build-bench/bench-build/bench_rss --hours 24 --interval 60 --hz 1 \
      > bench-results/rss_24h.csv 2> bench-results/rss_24h.err &

  # CSV 表头：elapsed_s,rss_kb,calls,errors
  # 画图（有 gnuplot 时）
  gnuplot -e "set terminal png size 1200,600; set output 'bench-results/rss_24h.png'; \
              set xlabel 'elapsed (s)'; set ylabel 'RSS (KiB)'; \
              plot 'bench-results/rss_24h.csv' using 1:2 with lines title 'RSS'"

  # 无 gnuplot 时用 Python
  python3 - <<'PY'
  import csv
  rows = list(csv.DictReader(open('bench-results/rss_24h.csv')))
  xs = [float(r['elapsed_s'])/3600 for r in rows]
  ys = [int(r['rss_kb']) for r in rows]
  if ys:
      print(f"hours={xs[-1]:.2f} rss_first={ys[0]}KiB rss_last={ys[-1]}KiB "
            f"delta={ys[-1]-ys[0]}KiB peak={max(ys)}KiB calls={rows[-1]['calls']} "
            f"errors={rows[-1]['errors']}")
  PY

  判读标准：稳定期 RSS 曲线应围绕一条水平线波动；若单调上升，优先怀疑
  UA_ReadResponse/UA_WriteResponse 出口或回调上下文泄漏，再跑 LSan 定位。
  errors 在任何长跑里都必须为 0。

7.4 高延迟 / 丢包 / 半开连接

  Linux 回环注入（需要 root；客户端与自起 server 都在 lo 上，正好只影响被测链路）：

  # 200ms 延迟
  sudo ./scripts/netem_faults.sh delay 200ms
  ./build-bench/bench-build/bench_latency --threads 8 --ops 4000 --batch 16 \
    | tee bench-results/latency_delay200.txt

  # 5% 丢包
  sudo ./scripts/netem_faults.sh loss 5%
  ./build-bench/bench-build/bench_recovery --api-cycles 20 --restart-cycles 10 \
    | tee bench-results/recovery_loss5.txt

  # 延迟 + 抖动
  sudo ./scripts/netem_faults.sh jitter 200ms 50ms

  # 半开连接：iptables 黑洞指定端口，SYN/数据被静默丢弃，不由内核 RST
  sudo ./scripts/netem_faults.sh halfopen 4890
  ./build-bench/bench-build/bench_latency --threads 1 --ops 20 --batch 1; echo "exit=$?"
  # 预期：单次调用在 timeoutMs 附近返回错误（不是立即且不是永久挂死），
  #       随后 recovery benchmark 能恢复到健康。
  sudo ./scripts/netem_faults.sh clear

  # 一条命令完成“注入→测→自动恢复”
  sudo ./scripts/netem_faults.sh with loss 5% -- \
       ./build-bench/bench-build/bench_latency --threads 8 --ops 2000 --batch 16

  注意：`tc netem` 作用于整个 lo，会同时影响本机其他回环流量；测完务必 clear。
  报告里要写明这是“本机回环注入”，不能等同于真实工业现场多跳网络。
