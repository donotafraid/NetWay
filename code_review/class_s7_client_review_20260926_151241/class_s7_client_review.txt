2. 以官方代码/文档为准的 SDK 运行事实
================================================================================
（以下引用全部来自 open62541 v1.4.14 源码；获取方式为 raw.githubusercontent.com/
 open62541/open62541/v1.4.14/...，与官方 1.4 文档
 https://open62541.org/doc/1.4/client.html 一致。）

[A] 客户端没有自己的线程，必须周期调用 UA_Client_run_iterate
    client.h 顶部原文：
      "the client does not yet contain its own thread or event-driven main-loop ...
       The user will have to periodically call UA_Client_run_iterate to ensure that
       asynchronous events are handled, including keeping a secure connection
       established."
    对应实现：Impl::runWatchdog() → callRunIterate()（ua.cpp:1544-1580, 2507）。

[B] isFullyConnected 看的是 noSession，不是 noNewSession
    src/client/ua_client_connect.c  v1.4.14：
      UA_Boolean
      isFullyConnected(UA_Client *client) {
          /* No Session, but require one */
          if(client->sessionState != UA_SESSIONSTATE_ACTIVATED && !client->config.noSession)
              return false;
          if(client->channel.state != UA_SECURECHANNELSTATE_OPEN)
              return false;
          ...
      }
    结论：你的封装把 noReconnect / noNewSession 都固定为 true（ua.cpp:1369-1370），
    但 isFullyConnected 只受 noSession 影响，所以同步服务调用仍会走 connectSync 补连。
    这一点上一轮报告判断正确。

[C] noNewSession 的真实语义：会话失效即主动断开
    client.h 原文：
      "noNewSession: Don't automatically create a new Session when the intial one is
       lost. Instead abort the connection when the Session is lost."
    src/client/ua_client.c  processMSGResponse()：
      if(responseType != &UA_TYPES[UA_TYPES_ACTIVATESESSIONRESPONSE] &&
         (response->responseHeader.serviceResult == UA_STATUSCODE_BADSESSIONIDINVALID ||
          response->responseHeader.serviceResult == UA_STATUSCODE_BADSESSIONCLOSED)) {
          cleanupSession(client);
          if(client->config.noNewSession) {
              client->connectStatus = response->responseHeader.serviceResult;
              UA_LOG_ERROR(..., "Session cannot be activated ... The client is configured
                                 not to create a new Session.");
              closeSecureChannel(client);
          } else { ... }
      }
    结论：noNewSession=true 时，SDK 不会在服务调用里自动重建会话，而是把通道关掉、
    把 connectStatus 置成 BADSESSIONIDINVALID。恢复会话的责任落回封装层。

[D] initConnect 在通道未 CLOSED 时直接返回
    src/client/ua_client_connect.c  initConnect()：
      if(client->channel.state != UA_SECURECHANNELSTATE_CLOSED) {
          UA_LOG_WARNING(client->config.logging, UA_LOGCATEGORY_CLIENT,
                         "Client connection already initiated");
          return;
      }
    这是第 4.2 节"看门狗盲区"的直接原因：只要通道还 OPEN，connect()/connectSync()
    都无法真正重建会话。

[E] 同步服务调用会自动补连
    src/client/ua_client.c  __Client_Service()：
      if(!isFullyConnected(client)) {
          UA_LOG_INFO(..., "Re-establish the connction for the synchronous service call");
          connectSync(client);
          if(client->connectStatus != UA_STATUSCODE_GOOD) {
              respHeader->serviceResult = client->connectStatus;
              return;
          }
      }
    注意：connectSync 不会重置 connectStatus；重置只发生在 connectInternal()。
    因此 [C] 里被置为 BADSESSIONIDINVALID 之后，同一次 batchRead 的内部重试即使
    再进 connectSync 也拿不回 GOOD——这也是为什么 [C] 的状态必须由显式 connect()
    （走 connectInternal → 重置 connectStatus）来收拾。

[F] 配置浅拷贝与 logger 所有权（上一轮 R1 已被正确修复）
    client.h：UA_Client_newWithConfig "Moves the config into the client with a shallow copy."
    ua_client.c：UA_Client_delete → UA_Client_clear → UA_ClientConfig_clear
      if(config->logging != NULL && config->logging->clear != NULL)
          config->logging->clear(config->logging);
    你的 RealSdk::clientNew 现在在 setDefault 失败与 newWithConfig 失败两条路径都补了
    UA_ClientConfig_clear（RealSdk.h:22, 41），静态 logger 的 clear=nullptr 也不会二次释放。
    这处 OOM 泄漏已消除。

3.1 资源泄漏（UA_ReadResponse 出口路径）                       结论：A-
  - ReadRequestGuard / ReadResponseGuard / WriteRequestGuard / WriteResponseGuard
    四个 RAII 覆盖 batchRead/batchWrite 的全部出口：正常、重试、预算超限、
    逐项错误、参数校验提前失败、服务层错误、畸形响应（results==nullptr 且 size>0）。
    response 声明在 for 循环体内，Guard 每轮构造/析构，重试不累积。
  - 上一轮 R1（RealSdk::clientNew 的 OOM 泄漏）已修复并落盘：两条失败分支都
    调用 UA_ClientConfig_clear（RealSdk.h:22, 41）。本轮未发现新泄漏；
    全量 ASan(detect_leaks=1)+UBSan 121 用例 0 泄漏报告。

  仍建议（非缺陷，异常安全）：
    (E-1) ua.cpp:735-740 的出口顺序对"ISdk 抛异常"不设防：
            UA_ReadResponse response;
            {
              std::lock_guard<std::recursive_mutex> sdkLock(m_sdkMutex);
              response = m_sdk->serviceRead(client.get(), request); // ★
            }
            ReadResponseGuard guard(&response);
          ISdk 是 C 实现，正常情况下不抛；但它是可注入的虚接口，Mock/未来 SDK
          一旦抛异常，response 尚未构造 Guard，且它本身是未初始化的 POD。
          低风险，但既然你把 ISdk 当接缝，建议在公共入口再包一层 try/catch
          把 std::bad_alloc / std::exception 转成 RichError::INTERNAL_ERROR，
          让 Result 契约不被异常穿透。

3.2 配置快照与悬垂指针                                         结论：A-
  - ClientConfig 是纯值类型；create 入参按值拷贝，Impl::m_config 再拷贝一份，

3.3 线程安全（基于 v1.4.14 实际行为）                          结论：B
  事实基础见第 2 节 [A][B][C]。
  做得好的：
    - m_connState 用 CAS 做 connect/disconnect 单飞；m_lifeState 用 CAS 迁移且
      TurnToRunning()/setGiveUpSignal() 刻意用 CAS 防丢失更新（T100 验证粘性）。
    - InFlightGuard(m_taskCounter) 与 ApiLease(m_inFlight) 两套计数器边界清晰，

  扣分项：

4.1 【已修复，红→绿】disconnect() 之后 LifeState 与 isHealthy() 自相矛盾

          UA_SECURECHANNELSTATE_CLOSED)

问题原文（ua.cpp，getEffectiveStopSignal()）：

    return (m_shutdown.load(std::memory_order_acquire) &&
            !m_running.load(std::memory_order_acquire)) ||
           m_lifeState.load(std::memory_order_acquire) == LifeState::GIVEN_UP;

问题原文（include/OPCUAPacking/Types.h，LifeState 定义）：

    ///   sdkConnectStatus == GOOD

    ///   sdkSessionState  == ACTIVATED

    RUNNING,
后果：显式 disconnect() 成功后，m_lifeState 仍是 RUNNING；
      isHealthy() → 失败，checkLifeState() → RUNNING。
      两个只读 API 对"当前能不能读写"给出相反答案，且与 RUNNING 的文档定义冲突。
复现：tests/test34.cpp 的 T114。
修复：disconnect() 两条成功出口都调用 TurnToRecovring()（TurnToRecovring 的
      健康条件此时必然成立：sdkSessionState != ACTIVATED）。
      已在真机编译 + 全量回归验证：T114 修复前 FAIL，修复后 PASS；
      其余 120 个用例 0 失败。

4.2 【已定位，给出修复方向】看门狗不修复"通道 OPEN + 会话未激活"
--------------------------------------------------------------------------------
问题原文（src/OPCUAPacking/ua.cpp，doWatchdogDecision()！healthy 分支）：
    callRunIterate(client);
    auto checkCs = isChannelClosed();
    if(!checkCs)
    {
      TurnToRecovring();
      return;
    }
    auto connectResult = connect();
问题原文（ua.cpp，applyConfiguration()）：
  config->noReconnect = true;//固定设为true
  config->noNewSession = true;//固定设为true
后果：按官方 [C][D]，通道仍 OPEN 时 initConnect() 直接返回，connect() 无法重建
      会话；而 noNewSession=true 又让 SDK 不自动重建。于是该状态无自愈路径，
      只能耗到 giveUpThresholdMs → GIVEN_UP。
复现：tests/test34.cpp 的 T119（特征化：connectAsync 调用次数恒为 0，最终 GIVEN_UP）。
修复方向（本次未强行改生产代码，避免在无法真机复现该状态时引入新风险）：
  在 !healthy 分支中，当通道未 CLOSED 且 sdkSessionState != ACTIVATED 时，
  先 disconnect() 把通道打回 CLOSED，再走 connect()。伪代码：
      callRunIterate(client);
      if (sdkSessionState.load(std::memory_order_acquire) != UA_SESSIONSTATE_ACTIVATED) {
        (void)disconnect();          // 关掉 OPEN 的通道
        callRunIterate(client);
      }
      if (!isChannelClosed()) { TurnToRecovring(); return; }
      auto connectResult = connect();
  若采用该修复，请把 T119 从"特征化"改成"恢复后 isHealthy() 成功"的正向断言。

4.3 【已修复，红→绿】connect() 在 SDK 时钟冻结时无界忙等
--------------------------------------------------------------------------------
问题原文（src/OPCUAPacking/ua.cpp，Impl::connect() 轮询，修复前）：
  auto start = pImplQuote->nowMsImpl();
  while (true) {
    ...
    auto elapsed = pImplQuote->nowMsImpl() - start;
    if (elapsed > static_cast<int64_t>(pImplQuote->m_config.timeoutMs)) {
      ...
    }
    ...
    // 没有 sleep / 没有墙钟兜底
  }
对照 disconnect() 反而有：
    std::this_thread::sleep_for(std::chrono::milliseconds(50));
后果：ISdk::runIterate 若立即返回且 nowMs 不推进（MockSdk 默认就是），
      elapsed 恒为 0，connect() 变成无界忙等：CPU 100%、永不返回。
      现有 T2 之所以没暴露，是因为它显式 setAutoAdvancePerIterateMs(50)。
复现：tests/test34.cpp 的 T120（修复前实测被 timeout 杀掉，exit=124）。
修复：加入 steady_clock 墙钟兜底（2*timeoutMs+500ms），并保留原虚拟时钟判据。
      验证：T120 修复前 timeout，修复后 900ms 内返回 CONNECT_TIMEOUT；
      T2/T74 等依赖虚拟时钟的用例仍然通过（全量回归 0 失败）。

4.4 【测试盲区，已补 T115】NodeId.ns 从未被断言
--------------------------------------------------------------------------------
问题原文（tests/include/MockSdk.h，serviceRead 的观察点，修复前）：
      lastReadNodeIdLengths_.clear();
      for (size_t i = 0; i < req.nodesToReadSize; ++i) {
        lastReadNodeIdLengths_.push_back(
            req.nodesToRead[i].nodeId.identifier.string.length);
      }
只记录了字符串长度，从不记录 namespaceIndex。若有人把 UA_NODEID_STRING_ALLOC 的
ns 参数写死为 0，现有 100+ 用例全部照样通过。本轮在 MockSdk 增加
lastReadNamespaces()/lastWriteNamespaces()，T115 钉死读 ns=7、写 ns=9 的透传。

4.5 【测试盲区，已补 T116/T117】真实 SDK 的断连连往返与数值往返
--------------------------------------------------------------------------------
- 没有任何用例做"显式 disconnect → connect → 再真实读"（T32 只验证断开后
  checkConnected() 失败，没验证还能连回来）。这正是计划检修后恢复采集的主路径。
- 真实服务器上只验证过 STRING 往返（T94），没有数值写回读；T95 只验证单个无效项，
  没有"同一次批量里混合有效/无效 + 索引对齐"。
  T116/T117 补上；T117 同时校验逐项索引对齐（out[0] 有效、out[1] Bad）。

4.6 【测试盲区，已补 T118】只测过 PROFILE_LOCAL
