3. 以官方源码为准的 SDK 运行事实与路径图
================================================================================
（行号均来自本机 /root/open62541-v1.4.14-noSanitizer 源码。）

[A] 客户端没有自己的线程，必须周期调用 UA_Client_run_iterate
    include/open62541/client.h:46-50 原文：
      "**However**: At this time, the client does not yet contain its own thread
       or event-driven main-loop, meaning that the client will not perform any
       actions automatically in the background. ... The user will have to
       periodically call `UA_Client_run_iterate` ..."
    对应封装：Impl::runWatchdog() → callRunIterate()（ua.cpp）。

[B] UA_Client_run_iterate 在 event loop 期间**释放** SDK 自己的 clientMutex
    src/client/ua_client.c 原文：
      UA_Client_run_iterate(UA_Client *client, UA_UInt32 timeout) {
          lockClient(client);
          UA_StatusCode rv = __UA_Client_startup(client);
          unlockClient(client);
          ...
          /* All timers and network events are triggered in the EventLoop. Release
           * the client lock before. The callbacks from the EventLoop take the lock
           * again. */
          UA_EventLoop *el = client->config.eventLoop;
          rv = el->run(el, timeout);      // ← 最多阻塞 timeout 毫秒
          ...
      }
    → 看门狗那 50ms 的阻塞只被封装层的 m_sdkMutex 持有，不是被 SDK 持有。
      也就是说，是封装自己把业务线程挡在门外。

[C] 同步服务调用全程持有 SDK clientMutex
    src/client/ua_client.c 的 __UA_Client_Service：
      lockClient(client);
      __Client_Service(client, request, requestType, response, responseType);
      unlockClient(client);
    → UA_Client_Service_read/write 都走这里；8 线程业务调用在 SDK 层本来
      就会串行，封装层的 m_sdkMutex 是在此之上再加一层。

[D] isFullyConnected 看 noSession，而不是 noReconnect/noNewSession
    src/client/ua_client_connect.c 的 isFullyConnected：
      if(client->sessionState != UA_SESSIONSTATE_ACTIVATED && !client->config.noSession)
          return false;
      if(client->channel.state != UA_SECURECHANNELSTATE_OPEN)
          return false;
    → 封装固定 noReconnect/noNewSession=true，但同步服务调用前的补连仍会走
      connectSync。

[E] noReconnect / noNewSession 的真实语义（client.h:112-116 原文）
      "noReconnect; /* Don't reconnect SecureChannel when the connection is lost
                     * without explicitly closing. */"
      "noNewSession; /* Don't automatically create a new Session when the intial
                      * one is lost. Instead abort the connection when the Session
                      * is lost. */"
    → noReconnect 不阻止同步服务调用前的 connectSync；noNewSession 才会在
      会话丢失时主动断开通道。

[F] 本轮新增：UA_Server_run_iterate(server, true) 的阻塞**有上界**
    src/server/ua_server.c:652 原文：
      #define UA_MAXTIMEOUT 500 /* Max timeout in ms between main-loop iterations */
    src/server/ua_server.c 的 UA_Server_run_iterate：
      UA_UInt32 timeout = (waitInternal) ? UA_MAXTIMEOUT : 0;
      el->run(el, timeout);
    并且 open62541 官方 server 主循环本身就用 true：
      src/server/ua_server.c:917  UA_Server_run_iterate(server, true);
    另有 1s 的 housekeeping 定时器（ua_server.c:742-744：
      /* Add a regular callback for housekeeping tasks. With a 1s interval. */）。
    → 所以 waitInternal=true 既不会空转一个核，也不会无限阻塞：
      每轮最多 500ms 返回一次。这条事实是本轮修测试 fixture 忙等的依据。

3.1 路径图 A：延迟尾巴的根因（业务调用 vs 看门狗 runIterate 争 m_sdkMutex）
--------------------------------------------------------------------------------

    业务线程 batchRead                         看门狗线程 runWatchdog()
    ------------------                         -----------------------
    lock(m_sdkMutex)  ──┐                       callRunIterate()
                        │ 竞争                  └─ lock(m_sdkMutex)  ← 先到者持有
    __UA_Client_Service │                          UA_Client_run_iterate(c, 50)
      lockClient()      │                            lockClient(); ...; unlockClient();
      ... 阻塞 ...      │                            el->run(el, 50)   ← 最多 50ms
      unlockClient()    │                          unlock(m_sdkMutex)
    unlock(m_sdkMutex) ─┘
                                                    等 100ms ... 循环 ...

    · 看门狗每轮先 sleep_for(100ms)，再 callRunIterate(50ms)。在链空闲时，
      那 50ms 是实打实的阻塞；业务线程想进 service 就得排队。
    · 线程扫描的数据与之吻合：p99 随并发线程数单调上升。
    · 修复方向（判断题，本轮未强改）：给 callRunIterate 加 timeout 形参，
      看门狗路径传比 50ms 更小的值（例如 0，非阻塞 iterate + 100ms 轮询），
      connect/disconnect 的轮询路径保留 50ms。这样既不丢事件，又消掉 50ms
      的锁持有。这是「面试会被问、且你有数据支撑」的取舍点。

--------------------------------------------------------------------------------
3.2 路径图 B：测试 fixture 忙等一个核（本轮已修）
--------------------------------------------------------------------------------

    修复前 tests/util/ClientTestFixture.cpp（两处）：
      serverThread_ = std::thread([this] {
          while (running_.load(std::memory_order_acquire)) {
              UA_Server_run_iterate(server_, false);   // ← waitInternal=false
          }
      });

    → false 时 el->run(..., 0) 立即返回，while 变成纯忙等，占满一个 CPU 核。
      每个用到 ClientTest fixture 的用例都起这样一个线程；在一台 4 核 8 线程
      机器上它同时和被测线程抢 CPU，会把 sleep/超时类用例的时序推向边界。
      第六轮只把 bench 的同类问题修成 true，漏了 tests fixture。本轮修掉，
      并把注释同步改对（见补丁）。修复后全集 143 用例 64.4s 跑完、142 PASS。

3.3 路径图 C：同一 UA_Server* 可以 stop/start（证明 restart benchmark 合法）
--------------------------------------------------------------------------------
    bench_recovery 用 server->stopServing()/startServing() 模拟服务端宕机。
    官方源码证明这是受支持的：
      UA_Server_run_startup 开头：if(server->state != UA_LIFECYCLESTATE_STOPPED)
        { ... "The server has already been started" ... return BADINTERNALERROR; }
      UA_Server_run_shutdown 结尾：setServerLifecycleState(server,
        UA_LIFECYCLESTATE_STOPPED);
    → run_shutdown 把状态复位 STOPPED，因此可再次 run_startup。restart_recovery
      的测量对象合法。

4.10 库本体：本轮没有发现新的会导致失败的缺陷（正面结论）

  我把资源出口、配置快照、线程安全、Rule of Five、封装完整性又过了一遍，
  重点核对了你点名的 UA_ReadResponse 出口：
    · ReadResponseGuard / WriteResponseGuard 对
      `results==nullptr && resultsSize>0` 与
