2. 以官方代码/文档为准的 SDK 运行事实
================================================================================
（以下引用全部来自本机 v1.4.14 源码，行号为该文件真实行号。）

[A] 客户端没有自己的线程，必须周期调用 UA_Client_run_iterate
    include/open62541/client.h:46-50 原文：
      "At this time, the client does not yet contain its own thread or
       event-driven main-loop ... The user will have to periodically call
       UA_Client_run_iterate to ensure that asynchronous events are handled,
       including keeping a secure connection established."
    对应实现：Impl::runWatchdog() → callRunIterate()（ua.cpp:1580-1591）。

[B] isFullyConnected 看 noSession，而不是 noReconnect/noNewSession
    src/client/ua_client_connect.c:121-128 原文：
      UA_Boolean isFullyConnected(UA_Client *client) {
          if(client->sessionState != UA_SESSIONSTATE_ACTIVATED &&
             !client->config.noSession) return false;
          if(client->channel.state != UA_SECURECHANNELSTATE_OPEN) return false;
          ...
      }
    结论：封装把 noReconnect / noNewSession 固定为 true（ua.cpp:1403-1404），
    但 isFullyConnected 只受 noSession 影响 → 同步服务调用仍会走 connectSync。

[C] noReconnect 的真实语义：只禁止“被动失联后的后台重连”
    client.h:112-114 原文：
      "noReconnect: Don't reconnect SecureChannel when the connection is lost
       without explicitly closing."
    → 不阻止同步服务调用前的 connectSync 补连。

[D] noNewSession 的真实语义：会话失效即主动断开通道
    client.h:114-116 原文：
      "noNewSession: Don't automatically create a new Session when the intial
       one is lost. Instead abort the connection when the Session is lost."
    src/client/ua_client.c:465-487 原文：
      if(responseType != &UA_TYPES[UA_TYPES_ACTIVATESESSIONRESPONSE] &&
         (serviceResult == UA_STATUSCODE_BADSESSIONIDINVALID ||
          serviceResult == UA_STATUSCODE_BADSESSIONCLOSED)) {
          cleanupSession(client);
          if(client->config.noNewSession) {
              client->connectStatus = response->responseHeader.serviceResult;
              closeSecureChannel(client);
          } else { ... }
      }
    结论：noNewSession=true 时 SDK 不会在服务调用里自动重建会话，而是关通道、
    把 connectStatus 置成具体 Bad 码。恢复会话的责任落回封装层。

[E] 同步服务调用会自动补连
    src/client/ua_client.c:569-578 原文：
      if(!isFullyConnected(client)) {
          UA_LOG_INFO(..., "Re-establish the connction for the synchronous service call");
          connectSync(client);
          if(client->connectStatus != UA_STATUSCODE_GOOD) {
              respHeader->serviceResult = client->connectStatus; return;
          }
      }
    注意：connectSync 不重置 connectStatus，重置只发生在 connectInternal()。

[F] initConnect 在通道未 CLOSED 时直接返回
    src/client/ua_client_connect.c（initConnect 首段）原文：
      if(client->channel.state != UA_SECURECHANNELSTATE_CLOSED) {
          UA_LOG_WARNING(..., "Client connection already initiated");
          return;
      }
    → 通道还 OPEN 时，connect()/connectSync() 都无法真正重建会话。

[G] StatusCode 的“坏”必须按 severity 位判断，不能与泛型码等号比较
    include/open62541/types.h:163-166 原文：
      UA_INLINABLE(UA_Boolean UA_StatusCode_isBad(UA_StatusCode code), {
          return ((code >> 30) >= 0x02);
      })
    build/src_generated/open62541/statuscodes.h:22：
      #define UA_STATUSCODE_BAD 0x80000000
    → UA_STATUSCODE_BADSESSIONIDINVALID=0x80250000 与 0x80000000 永不相等。

[H] disconnectAsync 必须被 run_iterate 驱动到 CLOSED
    client.h:468-470 原文：
      "Disconnect async. Run UA_Client_run_iterate until the callback notifies
       that all connections are closed."
    → 封装用 getState 轮询 CLOSED 是正确方向；但“有界性”必须由封装自己保证。

4.1 【已修，红→绿】Impl::disconnect() 在 SDK 时钟冻结时无界阻塞
--------------------------------------------------------------------------------
问题原文（src/OPCUAPacking/ua.cpp，Impl::disconnect() 轮询，修复前）：
    // ★ 等待CLOSED就绪（超时上限 = timeoutMs）
    auto start = pImplQuote->nowMsImpl();
    while (true) {
      ...
      // 检查超时
      auto elapsed =  pImplQuote->nowMsImpl() - start;
      if (elapsed > static_cast<int64_t>(pImplQuote->m_config.timeoutMs)) {
        ...
        return Result<Unit, DisconnectErrorState>::error(
            DisconnectErrorState::TIMEOUT_NOTDISCONNECT);
      }
      ...
      std::this_thread::sleep_for(std::chrono::milliseconds(50));
    }
后果：ISdk::nowMs() 若冻结（MockSdk 默认 autoAdvanceMs=0）且 disconnectAsync()
      不推进通道状态，elapsed 恒为 0，循环每 50ms 醒来一次却永不超时 →
      disconnect() 无界阻塞。对照 Impl::connect() 已有 steady_clock 兜底
      （ua.cpp:1082-1084,1114-1116），两者健壮性不对称。
复现：tests/test35.cpp 的 T121（修复前实测被 timeout 杀掉，exit=124）。
修复：加入 steady_clock 墙钟兜底（2*timeoutMs+500ms），保留原虚拟时钟判据。
      修复后 T121 在 ~900ms 内返回 DISCONNECT_TIMEOUT。

4.2 【已修，红→绿】看门狗把“channel CLOSED + session ACTIVATED”标成 RUNNING
--------------------------------------------------------------------------------
问题原文（src/OPCUAPacking/ua.cpp，doWatchdogDecision() 修复前）：
    } else if (isConnectBad()) {
      if (shouldTriggerGiveUp()) { TurnToGiveup(); return; }
      callRunIterate(client);
      auto checkConnectBad = isConnectBad();
      if (!checkConnectBad) { TurnToRunning(); return; }
      ... disconnect() ... connect() ...
    } else {
      TurnToRunning();          // ★ 叶分支：未命中任何已知故障就当健康
    }
后果：三元组 (connectStatus=GOOD, channel=CLOSED, session=ACTIVATED) 时，
      session 分支不命中、isConnectBad(GOOD) 不命中 → 落 else →
      TurnToRunning()。于是 checkLifeState()==RUNNING，而 isHealthy()（要求
      channel==OPEN）必然失败。Types.h:281-286 明确定义 RUNNING =“三元组
      全就绪、可正常读写”，公共契约被破坏。
复现：T122（修复前实测 FAIL）。
修复：把第三分支条件改成 `isConnectBad() || !isHealthyCached()`，并先
      updateBadStatusTime() 记账；叶分支只在 isHealthyCached() 为真时可达。

4.3 【已修，红→绿】isConnectBad() 用等号比较具体 Bad 码
--------------------------------------------------------------------------------
问题原文（src/OPCUAPacking/ua.cpp:2616-2619）：
    bool OPC_UA_Client::Impl::isConnectBad() const {
      return sdkConnectStatus.load(std::memory_order_acquire) ==
             UA_STATUSCODE_BAD;
    }
后果：stateCallback 回传的是具体码（如 UA_STATUSCODE_BADSESSIONIDINVALID
      =0x80250000），与泛型 UA_STATUSCODE_BAD=0x80000000 永不相等，分支近乎
      死代码。官方判据是 UA_StatusCode_isBad()（types.h:163-166，按 severity
      位 ((code>>30)>=0x02)）。
复现：T123（修复前实测 FAIL：看门狗对具体 Bad 码零重连尝试）。
修复：改用 UA_StatusCode_isBad()。

4.4 【已修】run_tsan.sh 的并发过滤器完整性自查会自己 exit 1

的用例，未出现在 ALL_FILTERS 里就 MISSING=1、exit 1。
